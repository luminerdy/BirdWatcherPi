# BirdWatcherPi reliability implementation plan

**Baseline:** public commit `d08bbd3d92099dd5e7272720fed2758a0e82bbd4`. This is a proposed plan, not evidence that fixes or field gates have passed. Public issues #3–#8 were reviewed; all were open when checked. Work in a separate checkout and isolated data directory; do not change the running installation, schedules, GitHub, or private data while implementing or testing. Reconcile any separately tested storage-pressure changes with this baseline by review, not by blindly copying uncommitted work.

## Objective and boundaries

Prioritize reliable, useful photos and daily recording over exhaustive visitor counts. Preserve originals and selected keepers; existing owner-approved age/quota raw retention is distinct from recognition-based deletion, which remains prohibited without separate approval. Capture must remain independent of optional analysis and external services. Keep photos, labels, private paths, location, precise schedules, device identifiers and credentials out of public artifacts. No new uploads, production service installation, reboot, retention change, or live update is authorized by this plan. Honor the owner-approved capture window; agree on safe cutoff and lighting criteria privately.

## Milestone 0 — establish safety and repeatability (P0)

- Freeze baseline and document the actual private runtime/version separately; record differences without publishing deployment details. Confirm recovery contact, manual off switch, existing schedule, storage ownership and last-known-good rollback artifact with the owner. Never infer current liveness from an enabled schedule.
- On a non-live checkout, run the existing test suite and traceability checker; record commands, results and failures rather than assuming a pass. Use synthetic JPEGs and disposable storage only. Map each change to `docs/traceability.json`, `docs/TRACEABILITY.md`, relevant spec requirements and tests; update implementation/test/field statuses independently.
- **Gate:** isolated environment and rollback plan verified; existing failures documented; no live files or jobs touched. Do not block photo capture improvements on analysis or reporting.

## Milestone 1 — prevent transient motion loss (P0)

- In `runner.run_capture`, decouple detector observations (currently up to 8 Hz) from `capture.sample_fps` event updates. Latch the union of active regions between sample ticks, consume it exactly once at the next event update, and define and test pending-pulse handling on reconnect/close before resetting; preserve an eligible representative frame where safely possible, and explicitly report any unavoidable loss. Decide explicitly how simultaneous regions and the first detector observation behave. Do not treat stale activity as indefinitely active. Preserve bounded pre-roll and frame-save cadence; avoid inference or disk I/O in the producer path.
- **Tests:** use injected fake camera/detector and deterministic clock: activity appears and clears wholly between two save ticks; assert an event starts and representative JPEG is saved. Include overlapping/multiple regions, no motion, continuous motion, tick boundaries, reconnect/reset, stop/close with a latched pulse before the next tick, slow writer, and no phantom retriggers. Assert an eligible buffered frame is saved exactly once when feasible or that the loss is explicitly accounted for, while honoring the cutoff. Verify capture sample rate and writer bounds remain intact.
- **Gate:** regression demonstrably fails on baseline and passes on fix; event and saved frame are asserted, not only detector output; pending-pulse stop and disconnect behavior meets the explicit save-or-account criterion. Existing event/runner integration suite passes. This fixes observed software loss, not unmeasured real-world bird recall.

## Milestone 2 — storage failures, observability and recovery (P0; independent of live rollout)

- Address `_write_health` failures at periodic, reconnect and shutdown sites: choose and document bounded best-effort behavior, preserving clean shutdown and writer accounting. When health cannot be written, expose a sanitized error through an independent channel such as stderr and a nonzero run outcome; never claim a stale `health.json` is current. Report freshness and unavailable/unknown explicitly. Distinguish actual storage-full signals from generic I/O failure; use `EventStore.health()` and retain writer failure details safely. Avoid recursive writes and indefinite retry.
- Make `cli.main` return nonzero for `dropped_saves`, storage failures, and health-reporting failure even when frames were received. Define stable health keys, state transitions and whether capture continues or stops under each failure; prefer a controlled degraded/stop outcome over falsely reporting healthy. Update docs and consumers compatibly.
- Make `EventStore.apply` event-start creation transactional or safely recoverable if the first `event.json` write fails. On restart, safely identify only managed empty/incomplete artifacts; do not delete ambiguous content, photos, symlinks, unrelated files or keepers. Respect existing journal/recovery semantics.
- **Tests:** inject ENOSPC, EDQUOT and generic OSError at health temp creation/write/fsync/replace/cleanup and initial manifest creation; assert no unhandled crash, correct status/exit/fallback and no false `storage_full`. Exercise writer queue saturation and dropped starts/frames/end accounting; first-manifest failure then restart, repeated recovery, interrupted frame/manifest journal writes, corrupted/ambiguous artifacts, and immutable original hashes. Use a small disposable filesystem or mocks, never fill production storage.
- **Gate:** failure outcomes visible even when health file cannot be updated; stale health detectable; no originals lost or unrelated data deleted; restart is idempotent; baseline regression and full suite pass. Storage-pressure fix and live deployment are separate approval gates, not a single operation.

## Milestone 3 — analysis capacity and onboarding (P1)

- The `AnalysisQueue` defaults to at most 100 pending or running jobs (configurable down to 1); completed and failed rows are not counted against that job limit, and database storage has a separate budget. There is no completed-result cleanup lifecycle. Specify bounded backlog, explicit full/deferred accounting, retry/idempotency and a separately approved retention policy for derived queue/results. Do not prune pending work or raw photos; explain what happens when sustained input exceeds processing. Keep capture functional if analysis is unavailable, full or crashed. Document the current limit until a policy is accepted.
- Improve `doctor` output so zero enabled regions is an actionable warning and is not confused with a successful capture-ready configuration; preserve machine-readable output/exit compatibility intentionally. Provide a local, private, clearly bounded motion/region preview or an equivalent documented setup workflow, with camera-lock handling and no automatic image upload.
- **Tests:** queue at capacity, restart and repeated enqueue, completed-record aging under an approved policy, corruption/locked database, analysis crash while capture continues; zero/enabled region doctor, camera busy, preview cleanup and privacy. Synthetic fixtures only.
- **Gate:** operator can distinguish camera availability from capture readiness, see backlog/full conditions, and recover without deleting originals. Retention design must be approved before enabling deletion.

## Milestone 4 — reproducible project and offline automation (P1)

- Add public CI for supported Python environments: clean install, deterministic tests, lint and `python3 scripts/check_traceability.py --check`; keep hardware, models, network downloads, real photos and secrets out of required CI. Document minimum system prerequisites and test limitations. Do not label hardware/field tests as CI-validated.
- Clarify reusable public capture/analysis versus private scheduling, review, digest and credentials. Simplify setup only after verifying a fresh clean environment; include camera prerequisites, explicit configuration, doctor/snapshot and supervised daylight checks. Public docs use generic examples and contain no identifying data.
- **Gate:** clean-room instructions reproduce a working synthetic test run; CI configuration is reviewed and its actual run verified after authorized publication. Privacy review of all publication-bound diffs.

## Milestone 5 — isolated hardware validation and controlled rollout (P1; issue #8)

- Owner agrees on a validation protocol within the approved operating window, acceptance thresholds, evidence and maintenance window in advance. Use a separate camera/Pi or a disconnected test setup, independent disposable storage and no competing camera owner. Test cumulative sessions across multiple days, stopping by the approved cutoff; record time actually operating, gaps, thermal/resource limits, event counts, dropped saves and storage errors privately. Require an independently enforced absolute stop deadline; test that manual starts, scheduled starts and retries refuse to launch when the approved daylight window cannot be validated or the cutoff has passed. A timer is not a darkness sensor.
- Inject camera unplug/replug, process restart, interrupted writes, analysis failure and low disk; test lock exclusivity, actual capture after recovery, clean stop, health freshness and rollback. Any reboot, new supervisor or service installation requires separate approval. Test public changes against private orchestration contracts without disclosing settings.
- **Proposed release gates:** all automated tests and traceability checks pass; no unexplained image loss, writer drops, storage errors or silent health failures during agreed daylight soak; recovery produces valid readable images and manifests; known gaps and evidence are reviewed by owner. The existing `BW-ARELIAB-001` requirement sets a minimum of 24 cumulative daylight-only hours across multiple sessions, with no unhandled crash or unbounded memory/backlog growth; record CPU, resident memory, temperature, dropped frames and queue depth. Agree any stricter duration and additional numeric thresholds before testing, not retrospectively. No claim of missed-arrival recall without an independent reference.
- **Production change only after explicit approval:** verify current runtime and fresh independent backup/restore of configuration, selected keepers and necessary data; record last-known-good version, stop/start procedure, lock ownership and manual off switch. Stage reviewed artifact without changing active jobs. During an agreed daylight maintenance window, pause and verify all automatic launchers before stopping the recorder cleanly; establish exclusive camera ownership, deploy one version, and recheck the approved window and safe lighting immediately before every start. Check fresh health and a newly readable saved image/manifest, then monitor next approved sessions. Never run both recorders. If checks fail, first verify automatic launchers remain paused, stop the new version, restore the verified prior artifact and configuration while launchers stay paused, and confirm exclusive camera ownership. Check the approved window and safe lighting immediately before every manual or automatic start, including retries. Verify fresh capture before resuming scheduling, and report the gap. If the window closes or rollback verification fails, leave capture stopped and launchers paused; defer capture verification to the next approved window and notify the owner. Never delete photos to force recovery.

## Later work and traceability

- **#3** private daylight comparison/labels; separate evaluation by event and report sampling gaps. Independent reference needed for recall. **#4** validate candidate confirmation against seed/sway controls without deleting captures. **#6** keeper ranking and separate non-destructive crops depend on usable private reviewed examples. These support photo quality but do not block P0 reliability.
- **#5** optional observation report and **#7** species classifier are later, not prerequisites; do not promise counts or upload images. **#8** gates portable daylight automation/recovery and requires private source/runtime reconciliation plus owner-approved hardware testing.
- Risks: motion latching may lengthen events; storage fallback cannot guarantee a disk-written health record on a full filesystem; retention may delete valuable evidence if boundaries are wrong; synthetic tests cannot prove Pi/camera behavior; private orchestration may differ from public code. Review these explicitly at each gate and keep field evidence private.
